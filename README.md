# 抖店对账本机工具

这是面向一人公司的单用户本机应用。当前版本已经具备：

> GitHub 仓库只保存源代码和自动化测试。`var/`中的数据库、上传账单、日志、备份以及`sample-data/`中的本机样例不会上传。

- 本机网页启动入口；
- SQLite本地数据保存；
- 正式数据当前仍使用规则版本V1.1；以后启用的新规则只用于之后新建的任务，已有任务保留原规则版本，不静默重算历史结果；
- 创建和查看月度对账任务；
- 按成熟SaaS工作台的任务阶段拆分“月度任务 / 数据导入 / 对账工作台 / 经营报表 / 配置中心”五个独立页签；
- 桌面端采用紧凑的两行固定工作台：第一行合并品牌、主导航和本机状态，第二行合并当前任务、关键指标和任务状态；下方明细区占用全部剩余高度并独立横纵滚动；
- 新建任务改为页面右上角下拉面板，不再长期占用列表左侧空间；
- 正式环境首次打开不预置任务或结果；
- 空状态下可由用户主动点击“载入样例数据”，样例任务全程显示“样例”标识；
- 重复任务防护；
- 导入一个包含五张表的.xlsx工作簿；
- 配置中心可维护五张核心账单的Sheet名、别名、表头行、数据起始行、字段名和字段别名；
- 账单模板使用“复制草稿 → 平台样例文件测试 → 明确确认启用”流程；已发布版本不直接覆盖；
- 每次导入保留当时的账单模板版本，历史文件不因新模板发布而回写；
- 对账规则支持“复制草稿 → 编辑4个有边界参数 → 试算C01—C23 → 明确确认启用”；编辑后自动作废旧测试结论，未通过23个固定案例不能发布；
- 基础资料可维护企业主体和抖店店铺，新建月度任务改为下拉选择，停用店铺不删除历史任务；
- 新的售后状态或资金场景会自动进入待映射清单；用户选择标准值、生效日期并填写说明后，映射只影响之后导入的文件；
- 原Excel值、映射后值和映射版本快照分开保存，既有文件、任务和对账结果不因新映射被重算；
- 检查缺表、必要字段、数据行数和结算说明行；
- 逐行整理并保存订单、售后、结算、资金和成本数据；
- 检查空编号、错误金额、错误日期、重复编号和任务月份；
- 任务月份与Excel月份不一致时，界面可一键按识别月份生成修正任务并重新检查；原任务、原文件和原导入结果保留可追溯；
- 页面展示数据量、日期范围、阻断/提醒以及原Excel行号；
- 页面展示本次导入五张表的行数、源文件列数和关键金额汇总；
- 点击任一工作表汇总卡可以穿透到当前文件版本的真实底表，支持20/50/100行分页；
- 对账工作台收敛为“对账总览 / 对账明细 / 原始数据下拉框”；查看明细时不显示上传表单，也不再用十多个页签占据数据区；
- 可在数据导入页补充平台账户逐笔资金、日汇总和月汇总；“资料完整性”页同屏比较笔数、收入、支出、余额公式和日期覆盖，并可穿透到原Excel行；
- M017当前按模拟表头试运行：明确标记“模拟映射 / 不阻断完成本期”，不将模拟字段冒充成当前抖店正式导出能力；
- 可单独导入M018待结算订单和售后辅助资料；“待结算跟踪”按优先级区分正常等待、逾期、售后中、平台限制、资料不足和取消/退款排除，每笔可同时穿透主要与辅助Excel行；
- M018当前固定为`M018-SIM-1`模拟映射，使用2026-08-08 12:00模拟核对时点和规则版本的等待天数，只做试运行跟踪，不阻断完成本期；
- 默认“对账明细”是一张按子订单展开的统一宽表，把核对结论、订单、售后、结算、平台资金、成本和原Excel行放在同一行；无法关联子订单的平台资金仍单独保留，不会因合并而丢失；
- 宽表支持全部/待处理/一致/未进入结算/人工已处理筛选、业务场景筛选、编号搜索和20/50/100行分页；双层分组表头、前四个关键列固定，数据区独立横纵滚动；
- 同一子订单存在多笔售后、结算、资金或核对结果时，宽表先显示笔数和合计，点击“展开N项”查看全部证据并进入原有人工处理表单；
- 按R01—R03检查订单应付金额以及结算账单的订单总价、收入合计、支出合计和结算金额；
- 金额检查绑定文件版本、规则版本和容差，保留平台金额、系统计算金额、差额和Excel行号；
- 按R04核对`已结算`与`货款结算入账`：同一子订单、同一平台账户、入账方向、金额容差和最终唯一记录同时满足才自动通过；时差超过24小时保留预警；
- 普通结算结果在统一宽表中作为业务场景展示，保留本次汇总、状态筛选、结算金额、资金金额和资金流水号；
- 每条普通结算可穿透到结算账单与资金账单原Excel行，并继续打开对应底表；
- 按R05对结算后退款做净额归组：同一子订单、同一售后编号下将入账减出账，净额一致、组合唯一且售后单唯一为“退款成功”才能自动通过；
- 5分钟内可自动归组，5分钟以上至24小时只保留候选，超过24小时默认排除，多个合理售后组同时命中时停止自动判断；
- 退款结算在统一宽表中作为业务场景展示，保留结算净额、资金净额、售后编号、资金行数和最大时差，并可穿透到一笔结算行及多笔资金原始行；
- 在R05净额结果之后试算退款构成：连接退款前原结算、退款成功售后、退款结算和资金组合，分别展示顾客退款、预计/实际平台补贴追回；
- 退款构成明确标记为“外部课程公式试算”，不改变R05状态、不阻断完成本期；达人、抖音支付和月付等其他补贴不误套平台补贴公式；
- 内置7个大类、37个细分类的课程候选资金字典，默认关闭自动对应；未经当前店铺逐笔样本和税务规则确认，不自动记账或自动开票；
- 按R06执行“订单与结算”勾稽：已结算订单比较`订单应付+平台承担优惠+达人承担优惠`与`结算收入合计`；未进入普通结算的订单按已关闭、全额退款、正常等待、售后中和可能未结算分类；
- “缺少历史订单”作为资料问题单独展示，不误报为平台少结；超过等待期的已完成订单会进入待处理并阻止完成本期；
- 按R07区分退款成功、售后关闭和换货成功，同一订单多次售后仍保留每个售后单号；售后关闭/换货与退款结算、资金同时出现时显示冲突；
- 按R08用订单货号关联成本表型号，展示数量、单位静态成本和订单静态成本；缺货号、缺成本或多候选均不自动通过；
- 按R09—R10将月付贴息、运费险类、消费者赔付和提现单独分类；新费用进入等待分类，不并入普通结算差异；
- 订单与结算、售后状态、成本关联和其他收支统一进入宽表的业务场景筛选；售后金额拆分为“申请退款”和“成功退款”，不再把售后关闭/换货金额当作已退款；
- 待处理明细可直接人工确认、选择候选、调整金额或带到下月；处理原因必填，调整金额默认为空，带到下月必填预计日期；
- 系统原结论不被覆盖，人工结论、原因、候选/金额/日期和每次修改历史单独保存；
- 顶部“完成本期”会先展示处理链路、阻断、人工处理、带到下月、未处理和规则版本；存在未处理记录时不允许完成；
- 完成后任务只读，不能重传文件或修改人工结论；填写原因重新打开后恢复编辑，原完成记录继续保留；
- 六类分类结果的XLSX导出继续保留；统一宽表可按当前状态、业务场景和编号搜索导出全部明细，不受页面分页限制；
- 导出文件固定包含“导出说明”和“对账结果”两个工作表：任务、文件版本、规则、筛选和行数可追溯，编号按文本保存，金额和日期使用可计算、可排序的Excel类型；
- 每次导出记录结果类型、筛选条件、行数和文件名，不覆盖系统或人工结论；
- 新增独立“经营报表”页，只统计当前任务最新文件版本，展示结算收入、平台结算支出、结算净额、退款成功金额和静态成本试算；
- 经营报表页明确标记“平台账单口径经营分析”；成本、履约和经营费用未齐时，店铺经营利润为空并显示“暂不计算”，不用0元或虚构金额代替缺失资料；
- 页面同时展示M017-B—M022-B的Pending资料及其解锁结果，并列出“对账结果明细 / 店铺月度经营利润表 / 经营报表中心 / 正式会计利润表”的当前范围和状态；
- 经营报表页支持提交ERP历史成本、快递/仓储和经营费用三类原始资料，保存多个版本并要求填写替换说明；收到文件只标记“待映射”，不会直接进入利润计算；
- 样例任务已用明确标识的造数打通ERP成本退货、快递仓储费、经营费用和店铺利润试算；模拟文件不能导入真实店铺任务；
- 模拟利润每个金额可查看对应资料的匹配行、编号、金额、原值和Excel行；正式利润仍等待真实资料确认；
- 用SHA-256阻止相同文件重复导入；
- 重传时保留旧文件并记录原因；
- 任务创建和文件导入操作记录；
- C01—C23固定案例可以一键运行并得到23/23明细结果；
- 创建、导入、核对、异常阻断、完成、导出和重新启动已纳入全流程自动检查；
- 可生成包含数据库和上传文件的校验备份包，恢复前自动检查文件内容和数据库完整性；
- 恢复已有数据时，先把恢复前数据完整保存在`recovery-before-restore-*`目录；
- 健康检查和关键路径自动测试。

## 样例数据

应用不会自动载入样例。如需使用“载入样例数据”，请将已脱敏的五表工作簿保存为`sample-data/抖店练习数据.xlsx`，或通过环境变量`DOUYIN_RECONCILIATION_SAMPLE`指定路径。样例文件默认不进入Git。重复点击会打开现有样例，不会重复创建。

现有本机样例任务可另外载入带`SIMULATED_FOR_PRODUCT_VALIDATION`标识的经营资料工作簿。该造数只会产生“模拟试算”，不得作为真实店铺利润或生产效果证明。

开发与浏览器自动验收必须使用临时数据目录，不得再向正式`var`目录写测试任务。

## 启动

需要Python 3.9或更高版本，不依赖第三方Python包。克隆仓库后，在macOS可直接运行：

```bash
git clone https://github.com/pmjaynechen/douyin-reconciliation.git
cd douyin-reconciliation
./start.command
```

在Finder中双击`start.command`，或在终端进入本目录后运行：

```bash
./start.command
```

浏览器打开：<http://127.0.0.1:8766>

终端窗口需要保持打开；运行期间不要关闭该窗口。需要停止时，在该窗口按`Control+C`。重复启动时会先检查已有服务，不会生成第二个进程。

## 数据位置

- 数据库：`var/reconciliation.db`
- 上传文件：`var/uploads/`

不要只复制数据库而遗漏上传文件。推荐使用下面的备份入口。

## 备份

1. 在运行应用的终端窗口按`Control+C`停止应用。
2. 在Finder中双击`backup.command`。
3. 系统检查数据库后生成ZIP备份，默认保存到`文稿/抖店对账备份/`。

备份包包含数据库和所有已上传的Excel文件，并记录每个文件的大小和内容校验值。服务仍在运行、数据库无法读取或文件在复制过程中变化时，系统会停止并说明原因，不会生成一个看似成功的备份。

也可以在终端执行：

```bash
python3 app.py --backup
python3 app.py --backup --backup-dir "/自定义/备份目录"
python3 app.py --verify-backup "/备份目录/备份文件.zip"
```

## 恢复

1. 在运行应用的终端窗口按`Control+C`停止应用。
2. 双击`restore.command`，选择一个备份ZIP。
3. 核对文件名后输入“恢复”。
4. 恢复完成后重新双击`start.command`。

恢复前会检查ZIP中的文件清单、文件内容和数据库是否完整。当前`var`不会被直接删除，而是移动到应用目录旁的`recovery-before-restore-日期-*`目录。选错备份或发现数据不符合预期时，恢复前的数据仍然保留。

备份和恢复都会校验文件清单、内容校验值与SQLite完整性；恢复前数据会先移入`recovery-before-restore-*`目录。

## 自检与测试

不依赖本机Excel样例的便携测试：

```bash
python3 app.py --self-check
PYTHONPATH=tests python3 -m unittest -v \
  test_backup_restore test_end_to_end test_export_xlsx \
  test_fund_category_catalog test_refund_component_fixture test_server
```

完整回归和C01—C23固定案例依赖不入库的脱敏Excel样例，只在本机项目目录执行：

```bash
python3 app.py --fixed-cases
python3 -m unittest discover -s tests -v
```

`--fixed-cases`会逐项输出C01—C23结果，只有23项全部通过才返回成功。`start.command`默认使用电脑上的`python3`，也可用`DOUYIN_RECONCILIATION_PYTHON`指定Python可执行文件。当前应用版本为0.24.0、数据结构版本为19；本机完整回归为105项，GitHub Actions只运行不依赖本机数据的便携测试和应用自检。

## 当前边界

- 仅绑定`127.0.0.1`，不对局域网或公网开放；
- 单用户，不含登录、角色和审批；
- 只支持`.xlsx`，单个文件最大50MB；不支持`.xls`、加密文件或宏文件；
- 当前账单模板、4个有边界的对账参数、主体/店铺和售后状态/资金场景映射已可维护；公式、匹配主键、证据条件和硬校验仍不允许任意修改；
- 平台值映射只影响生效日期之后的新导入；原Excel值和当时使用的映射版本始终可追溯，不会静默重算历史结果；
- 默认7天结算等待规则已用订单完成时间执行并有边界测试；如将来取得平台预计结算日，应优先使用平台日期；
- 仅靠当前订单文件无法证明平台导出无漏行；当前已阻止订单文件混入多个月份，完整性总量仍需平台导出摘要或接口对账；
- 平台账户日/月汇总已可按模拟映射检查明细漏行、笔数、金额、余额公式、账户和月份；取得真实抖店文件前结果只作为资料完整性提示，不阻止完成本期；
- 待结算订单已按模拟映射分类并保留两张源表证据；当前核对时点是模拟参数，真实文件到位前不作为平台超时或少结的正式结论；
- 成本表没有生效日期，因此当前只展示静态成本测算，不声称是正式历史利润；
- M022-B0只在样例任务中识别明确标识的模拟工作簿；真实店铺会拒绝该文件，M020、M021和M022-B仍需真实样本后才能变为正式能力；
- 多组退款候选会停止自动通过并保留候选；用户可在明细中选择候选并填写原因，系统原结论与历次人工结果均保留；
- 退款构成比例公式来自课程资料，当前只试运行；取得真实部分退款样本前不作为平台正式规则；
- 资金分类字典来自汇总附件，不含逐笔对应条件，当前不会自动改变其他收支分类；
- 结构化订单和售后数据不复制收件人、手机号和地址等无关个人信息；
- 底表展示的是已入库的对账必要字段，不等于把Excel所有原始列完整复制到页面；
- 统一宽表在页面查询和导出时均组合现有数据，不新增一份重复财务事实；导出上限10万行，超过时需缩小场景或编号范围；
- 不处理银行流水、正式会计利润或凭证。
